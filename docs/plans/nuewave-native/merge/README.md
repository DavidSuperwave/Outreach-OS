## The ruling set (2026-08-19, confirmed by David)

These eight rulings were made in a structured grill and confirmed as a set.
They supersede earlier decisions where they conflict — most importantly the
old clean-room rules in `../roadmap.md` §2.

1. **Harvest rules (replaces clean-room).** Permission was obtained to use the
   Neuwave repo. Agents may read everything — Rust source, SolidJS frontend,
   OpenAPI specs, GraphQL schema, Postgres migrations, prompts — and write
   Cloudflare-native TypeScript equivalents, including **faithful UI/UX
   recreation**. Two tripwires remain:
   - **No Macro branding.** Icons, trade dress, the "Macro agent" identity —
     anything that is identity rather than function stays out.
   - **No Rust code reuse.** The Rust cannot run on Workers; everything is a
     rewrite. Reading it as reference is fine; copying it is not possible and
     not permitted. *Carve-out (2026-08-19, Q16):* the four services already
     running on Cloudflare (`sync-service` Rust/WASM, `lexical-service`,
     `ai-editing-worker`, ~~`coding-agent-worker`~~ *[corrected 2026-08-19,
     ruling A3: dropped — no source ever committed in any repo and never a
     CF Worker; the lift set is three services]*) are **lifted as-is** — the
     no-Rust rule targets the AWS-native Rust, not WASM already deployed on
     Workers. Their routes must be reconciled into the unified CF-OS route
     model as a first-class design task (the old AWS↔CF route-sync conflict
     is dead; route/service alignment inside one Cloudflare stack replaces it).
2. **Merge = full absorption.** Outreach-OS is the only surviving codebase.
   Every Neuwave capability gets exactly one verdict: rebuilt Cloudflare-native
   or explicitly killed. Nothing keeps running on AWS. (This inverts the
   original Nuewave Pilot plan, which kept Macro as the main platform and used
   CF-OS as a runtime layer — see `original-linear-plan-review.md`.)
3. **Linear endgame (D1).** One merged Linear project replaces both existing
   projects. Scope is written from this folder's final audit by a separate,
   explicitly-confirmed agent pass. Linear stays untouched until then.
4. **Name (D2).** Product: **Nuewave**. Merged Linear project title:
   **"Nuewave T"** (Linear-only marker so the team knows it is the
   post-decision project).
5. **Folder.** This subfolder (`docs/plans/nuewave-native/merge/`) is the merge
   home. No competing top-level plan folder.
6. **Reference state.** Neuwave `main` is cloned locally and pinned (below).
   Every code pointer in this folder resolves against that pinned state.
7. **Re-audit everything.** No verdict from the earlier concept-only docs
   (parity map, shell plan, capability map) survives on trust. Every capability
   gets fresh research against actual source before its rebuild-or-kill verdict
   is drafted. Known doc conflicts (e.g. Channels) get surfaced explicitly.
8. **Full endpoint extraction; schemas over, data doesn't.** Every endpoint
   from the OpenAPI specs, `schema.graphql`, and axum routers, plus frontend
   routes/splits, mapped against the CF-OS router model. The four Postgres
   databases hold no live data, but their **schemas** are harvested so the
   D1/Durable-Object storage design starts from the old data model, not zero.

## How the merge audit works

1. Research agents fill the inventories (endpoints, routes, schemas) from the
   pinned clone. Done in slices; each file states its own coverage.
2. The **merge ledger** joins everything: one row per capability, at the
   granularity of the thing a verdict is about (a domain crate, a UI split, a
   block type, a service). Each row carries: old code pointers, what it does,
   endpoint/schema cross-refs, proposed CF-native target, effort note, and an
   empty `Verdict:` slot.
3. David rules on ledger rows in batches (grill-style, concrete options).
4. When every row is ruled, the **final audit** is the ledger plus the ruling
   dates — and the Linear scope-map agent turns it into the "Nuewave T"
   project. That agent's contract is in `agent-brief.md`.
